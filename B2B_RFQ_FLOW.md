# B2B RFQ → Quotation → PO → Invoice → Payment Flow

End-to-end documentation of the **B2B marketplace** RFQ pipeline, traced through the codebase. The workspace/CRM pipeline is a separate flow and is called out only where the code paths diverge.

## Systems Involved

| Repo | Role |
| --- | --- |
| `B2B-Frontend` → `B2B-Backend` | Client-facing site. Client fills and submits the RFQ form. |
| `Employee_Main` (`auditor/` frontend → `backend/`) | Internal portal used by **Procurement**, **PM**, and **Finance** teams. |
| `Vendor_Frontend` → `Sales-Backend` | Vendor portal. The vendor's "Sales" module reads RFQs, quotations, and POs. |
| `Client_Frontend` → `Client_backend` | Client portal where the client approves quotations, uploads PO, and views invoices/payments. |

All persistence is **DynamoDB** (multiple services share the same tables), files go to **S3**.

## Flow, Step by Step

### 1. Client submits the RFQ form — *Client, via B2B*

- **Code:** `createRfq` — `B2B-Backend/controllers/rfqController.js:48`
- **Writes to:** `DYNAMODB_RFQS_TABLE` (PK `rfqId` = uuid, human ID `customRfqId` = `RFQ-DD/MM/YYYY-NNN` generated by counting today's RFQs)
- **Uploads to S3:** product images → `rfq_images/`, BOQ → `rfq_boq/`, CAD → `rfq_cad/`, tech docs
- **Status set:** `status: 'new'` (`rfqController.js:264`)
- Requires Cognito auth + a client profile (`req.clientProfile.clientId`), which is stamped on the record so downstream steps can resolve the client.

### 2. Procurement sends the RFQ to selected vendors — *Procurement team, via Employee_Main*

- **UI:** `auditor/src/procurement/pages/ProcurementHub.jsx` / `RfqManagement.jsx` → `POST /api/rfq/send`
- **Code:** `sendRfq` — `Employee_Main/backend/controllers/rfqController.js:8`
- **Writes to:** `DYNAMODB_SENT_RFQS_TABLE` — one record `{ sentRfqId, vendorIds[], enquiryId, material, quantity, specification, category, source: 'b2b', status: 'rfqsent', clientId, clientUserId }`
- **Status changes:**
  - `sent_rfqs.status` → `'rfqsent'`
  - source `DYNAMODB_RFQS_TABLE.status` → `'Sent'` (for `source='b2b'`; CRM path sets `procurement_requests.status` → `'RFQ Sent'`)
- Note: `vendorIds` is a single shared list — one `sentRfq` record covers all selected vendors.

### 3. Vendor sees the RFQ and sends a quotation — *Vendor, via Sales module*

- **List:** `getEnquiries` — `Sales-Backend/controllers/enquiryController.js:25` — queries `SENT_RFQ_TABLE` via `status-index` GSI for statuses `rfqsent` **and** `sent`, filtered `contains(vendorIds, :vendorId)`
- **Submit:** `sendQuotation` — `enquiryController.js:209`
- **Writes to:** `QUOTATION_OF_VENDOR_TABLE` — `{ quotationId, sentRfqId, enquiryId, vendorId, ...quoteDetails }` (**no status field is written**)
- **Status changes:** `sent_rfqs.status` → `'sent'`, `quotedAt` set — on the single shared record, regardless of which vendor quoted
- Auth: `vendorMiddleware` attaches `req.vendorId`; `getEnquiryById` re-verifies `vendorIds` membership.

### 4. Procurement reviews vendor quotes and creates the final quotation — *Procurement*

- **Read quotes:** `getQuoteByEnquiryId` / `getVendorQuotationsByEnquiryId` — `Employee_Main/backend/controllers/quotationController.js:185,243` — scans `QUOTATIONS_OF_VENDORS_TABLE` by `enquiryId`, enriches with vendor name.
- **Create final quote:** `createFinalQuotation` — `quotationController.js:445` → `POST /api/quotations/final`
  - **Writes to:** `DYNAMODB_QUOTATIONS` (final quotations table), PK `quotationsId`, with `rfqId = enquiryId`, `sourceVendorQuotationIds[]`, resolved `clientId`/`userId`, optional `paymentTerms`/`advancePercentage`
  - **Status:** `'Pending'`
- **Upload PDF:** `uploadFinalQuotationPdf` — `quotationController.js:540` → S3 `invoices/{quotationId}.pdf`, sets `pdfUrl`/`s3Key` on the record.
- **Send to finance:** `submitToFinance` — `quotationController.js:725`
  - **Status:** `final_quotations.status` → `'ReadyForFinance'` (re-resolves `clientId`/`userId` and back-fills them)

### 5. Finance adds commission and sends to client — *Finance team*

- **Code:** `saveB2BCommission` — `quotationController.js:789`
- **Writes to:** `b2b_quotations_with_commission` (`DYNAMODB_B2B_QUOTATIONS_WITH_COMMISSION`) — `{ commissionRecordId, quotationsId, clientId, commissionLines[], summary, metadata, paymentTerms, advancePercentage }`
- **Status changes:**
  - `final_quotations.status` → `'sent to client'`, `commissioned=true`, `lastCommissionedAt`
  - `b2b_quotations_with_commission.status` → `'sent to client'`

### 6. Client approves the quotation — *Client, via Client portal*

Two-step email-token approval in `Client_backend/controllers/workspaceQuotationsController.js`:

- **Initiate:** `approveB2bQuotationByClient` — `PATCH /client-api/workspace-quotations/b2b-quotations/:quotationId/client-approval` (`:637`)
  - Sends a confirmation email containing a token (24h expiry). **If the email fails, status is NOT updated.**
  - `b2b_quotations_with_commission.status` → `'Pending client confirmation'`, `clientApprovalStatus` → `'pending'`, stores `confirmationToken`, `tokenExpiry`, `ShipmentAddress`
  - Syncs the same fields into the `QUOTATIONS` table if the record exists there.
- **Confirm:** `confirmB2bQuotationApproval` — `PATCH .../confirm-approval` (`:1474`)
  - Validates token + expiry → `status` → `'Client approved'`, `clientApprovalStatus` → `'approved'`, `clientApprovedAt`, clears the token, syncs to `QUOTATIONS`, sends confirmation email + notification.

### 7. Client provides the PO — *Client*

Two options, both in `workspaceQuotationsController.js`:

- **Upload own PO:** `uploadClientPO` — `POST /client-api/workspace-quotations/upload-po` (`:1681`)
  - PDF only → S3 bucket **`client-po-uploads`**, key `client-po/{quotationId}/...` (re-uploads go to `revised-po/` and fill `revisedPOFile*` instead of overwriting)
  - Sets on the quotation (in `b2b_quotations_with_commission`, falling back to `workspace_quotations`): `clientPOFile`, `clientPOFileName`, `clientPOUploadedAt`, `poType: 'client'`, **`status → 'requested_po_from_pm'`**; syncs to `QUOTATIONS`.
- **Use our PO:** `useSystemPO` — `POST .../:quotationId/use-system-po` (`:1901`)
  - Sets `poType: 'system'`, `systemPOGeneratedAt`, and clears `clientPOFile*`. **⚠️ Does not set `status` — see Bugs.**

> **Scope note:** This document covers the **B2B marketplace flow** only. The workspace/CRM flow (PM strips commission, `WSPO-`/`WB2BPO-` POs in `workspace_purchase_orders`, `pm_approved_po`, etc.) is a *separate* pipeline and is not described here.

### 8. Procurement raises the PO and sends it to the vendor — *Procurement*

- **Code:** `createPurchaseOrder` — `Employee_Main/backend/controllers/purchaseOrderController.js:290` → `POST /api/purchase-orders`
- **Writes to:** `PURCHASE_ORDERS_TABLE` (PK `purchaseOrderId` = `PO-{uuid}`), with `quotationId`/`finalQuotationId`, `sourceVendorQuotationIds[]`, `rfqId`, `clientId`/`userId`, `vendorId`, `vendorDetails`, `products`, `totalAmount`, `poType` (client/system), `clientPOFile*` copied from the final quotation, server- or client-generated PDF → S3 `purchase-orders/{purchaseOrderId}.pdf`.
- **Status set:** `purchase_orders.status` → `'Raised'`
- **Status changes downstream:**
  - `final_quotations.status` → `'po raised for order'`
  - each source vendor quotation (`quotations_of_vendors`) → `'po raised for order'` + stamps `purchaseOrderId`
- Has special "building intent" handling (`rfq.enquiryIntent === 'building'`) to create one PO per vendor instead of a single PO.
- *(The `createWorkspacePurchaseOrder` / `createWorkspaceB2BProcurementPO` endpoints and the `savePmPOFile` "strip commission" step belong to the workspace/CRM flow, not B2B.)*

### 9. Vendor reviews, confirms the PO, and sends invoice to finance — *Vendor, via Sales module*

- **See PO:** `listPurchaseOrdersForVendor` / `getPurchaseOrderForVendor` — `Sales-Backend/controllers/purchaseOrderController.js:152,216` — `loadPoContextForVendor` resolves the PO from `purchase_orders` (B2B) or `workspace_purchase_orders` (workspace) and enforces `po.vendorId === vendorId`.
- **Confirm per PO line:** `updateVendorConfirmationForPoLine` — `purchaseOrderController.js:478` — `action: confirm | in_review | cancel` → stored in `po.vendorConformation[quotationId]` (`CONFIRMED` / `IN_REVIEW` / `CANCELLED`; `in_review` also stores `availableQuantity`, `remainingQuantity`, `remainingDeliveryDate`).
- **Attach invoice & send to finance:** `uploadInvoiceForPurchaseOrder` — `purchaseOrderController.js:271` — **requires the line to be `CONFIRMED`**, PDF only, no re-upload if `invoicePdfUrl` already exists → S3 `salesInvoices/{vendorId}/{poId}/{quotationId}/`
  - Sets `invoicePdfUrl`, `invoiceUploadedAt` on the PO.
  - **Auto-creates a `b2b_invoices` record** (`commissionRecordId` PK): `status: 'Raised'`, `source: 'sales'`, `summary { base, commission: 0, total }`, `commissionedInvoicePdfUrl: null`, carrying `purchaseOrderId`, `quotationId`, `vendorId`, `clientId`, products, `totalAmount`.
  - ⚠️ For the B2B path (`purchase_orders` table, `isWorkspaceB2B=false`) the PO row's `status` is **not** advanced to `'sent to finance'` — only the workspace path does that. The `b2b_invoices` record (status `'Raised'`) is what finance picks up.

### 10. Finance adds commission, sends to client; client pays → order placed — *Finance → Client*

- **Commission the invoice:** `updateB2BInvoice` — `Employee_Main/backend/controllers/b2bInvoiceController.js:169` (`PUT /api/b2b-invoices/:commissionRecordId`) — sets `commissionLines`, `summary { base, commission, total }`, `status` → `'commission applied'`, `commissionedInvoicePdfUrl` (commissioned PDF generated/uploaded in `finance/routes/workspaceInvoices.js:827`), optional `srFinanceApprovalStatus` (senior-finance approval). *(The sync-back to `workspace_purchase_orders` only runs for `crm_workspace` sources, so it's skipped in the B2B path.)*
- **Client reviews & pays:** the client sees the commissioned invoice and pays **as per the payment terms** (`paymentTerms`, `advancePercentage`) that procurement defined back at step 4 when creating the final quotation and sending it to finance — those terms were carried into `b2b_quotations_with_commission` at step 5.
- **Finance confirms payment:** `POST /finance/workspace-invoices/confirm-payment` (`finance/routes/workspaceInvoices.js:559`) → `workspace_invoices.paymentStatus → 'payment confirmed'`, `confirmedAt`, `confirmedBy`, and emails the client a payment confirmation.
- **Order placed:** once payment is confirmed, the order is considered placed.
- **Client visibility:** `getRecentPaymentHistory` — `Client_backend/controllers/workspaceQuotationsController.js:2030` — shows invoices with `paymentStatus` `'pending confirmation'` or `'payment confirmed'`.

## What Happens After the Client PO

```text
Client uploads PO (or "use our PO")
        │
        ▼
quotation.status = 'requested_po_from_pm'  (b2b_quotations_with_commission)
        │
        ▼
Procurement raises PO  → purchase_orders  (status 'Raised')
        │                 final_quotations → 'po raised for order'
        │                 vendor quotations → 'po raised for order' + purchaseOrderId
        ▼
Vendor sees PO in Sales module → CONFIRMS each line (vendorConformation[quotationId])
        │
        ▼
Vendor attaches invoice PDF → b2b_invoices auto-created (status 'Raised', source 'sales')
        │
        ▼
Finance adds commission to the vendor invoice → 'commission applied'
        │  (commissionedInvoicePdfUrl generated)
        ▼
Client reviews the commissioned invoice → pays per paymentTerms/advancePercentage
        │  (terms set by procurement at the final-quotation stage, step 4)
        ▼
Finance confirms payment → paymentStatus = 'payment confirmed'  →  ORDER PLACED
```

Finance touches the flow twice: once on the **quotation** (step 5, commission baked into the price the client approves) and once on the **vendor invoice** (step 10, commission added on top of what the vendor billed). The payment terms the client pays against are the ones procurement defined when creating the final quotation and sending it to finance.

## Status Reference (per table)

| Table | Status values observed |
| --- | --- |
| `rfqs` (B2B) | `new` → `Sent` |
| `sent_rfqs` | `rfqsent` → `sent` (+`quotedAt`) |
| `quotations_of_vendors` | none written by Sales-Backend; `'submitted'` by Employee_Main's `submitQuotation`; `'po raised for order'` after PO |
| `final_quotations` | `Pending` → `ReadyForFinance` → `sent to client` → `po raised for order` |
| `b2b_quotations_with_commission` | `sent to client` → `Pending client confirmation` → `Client approved` → `requested_po_from_pm` |
| `purchase_orders` (B2B) | `Raised` (+ `vendorConformation[quoteId]`, `invoicePdfUrl`) |
| `b2b_invoices` | `Raised` → `commission applied` (finance-set) |
| `workspace_invoices` | `paymentStatus`: `pending confirmation` → `payment confirmed` |
| `po.vendorConformation[quoteId]` | `CONFIRMED` / `IN_REVIEW` / `CANCELLED` |

Parallel field `clientApprovalStatus`: `pending` → `approved`.

## Bugs & Issues Found

1. **"Use our PO" is a dead end.** `useSystemPO` sets `poType:'system'` and clears `clientPOFile`, but never sets `status:'requested_po_from_pm'` — and procurement's PO-creation entry point (`createPurchaseOrder`) reads `clientPOFile*` off the final quotation. With `poType:'system'` and no client PO file, nothing downstream knows to generate/issue the vendor PO. A client choosing "use our PO" stalls the order.

2. **B2B PO status never advances past `'Raised'`.** `uploadInvoiceForPurchaseOrder` only sets `status → 'sent to finance'` when `isWorkspaceB2B` is true (workspace path). For the B2B path (`purchase_orders` table) it sets `invoicePdfUrl`/`invoiceUploadedAt` but leaves `purchase_orders.status` at `'Raised'`. Finance still finds the auto-created `b2b_invoices` record, but any UI filtering POs by status will show a PO that's already been invoiced as still "Raised".

3. **Shared `sent_rfqs` status flips on the first vendor quote.** `sendQuotation` sets `sent_rfqs.status='sent'` on the single record shared by all selected vendors (`enquiryController.js:247-266`). `getEnquiries` only keeps working because it deliberately queries both `rfqsent` and `sent`; there is no per-vendor state, so one vendor quoting changes what the record looks like for everyone.

4. **GSI query + `contains()` filter can silently drop vendor enquiries.** `getEnquiries` queries `status-index` with `Limit: 100` and applies `contains(vendorIds, :vendorId)` as a **FilterExpression** — which DynamoDB applies *after* the limit. A vendor's enquiry can be paged out and never returned even though it exists.

5. **Two divergent vendor-quotation write paths.** Employee_Main's `submitQuotation` writes `status:'submitted'`; Sales-Backend's `sendQuotation` writes **no status at all**. Any code filtering vendor quotes by `status` misses the Sales-Backend records.

6. **Duplicate `customRfqId` race.** `generateCustomRfqId` (`B2B-Backend rfqController.js:22`) counts today's RFQs with a Scan and uses `count+1` as the sequence — two simultaneous submissions can mint the same ID. Also, an RFQ ID contains `/` characters (`RFQ-DD/MM/YYYY-NNN`), which is awkward anywhere it's used in a URL or S3 key.

7. **Mislabeled endpoint.** `getQuotationsByEnquiryId` (`Employee_Main quotationController.js:157`) scans `sent_rfqs` and returns *RFQ records* — not quotations.

8. **Status naming is inconsistent** — mixed casing and formats across the pipeline (`Sent` / `rfqsent` / `sent` / `sent to client` / `Client approved` / `requested_po_from_pm` / `Raised` / `commission applied`), plus two overlapping fields (`status`, `clientApprovalStatus`) that must be kept in sync manually. Any consumer filtering on status has to know each table's exact spelling.

9. **Hardcoded S3 bucket in `uploadClientPO`.** Bucket is literally `'client-po-uploads'` (`workspaceQuotationsController.js:1719`) while the error message blames `AWS_S3_BUCKET_NAME`; region isn't set on that S3 client, so it falls back to ambient AWS config.

10. **Best-effort writes everywhere.** Quotation→PO→invoice propagation uses non-transactional multi-table writes with `catch { console.warn }` fallbacks (e.g. `createPurchaseOrder` updating `final_quotations` and each vendor quotation, `b2b_invoices` auto-create). A partial failure leaves the pipeline in a state the next step can't find — with no retry or reconciliation.
